# Product-Native UI

## Objective

Design interfaces that feel like real, mature, actively used software. The user came to use the product, not attend a presentation about it.

## Do not create presentation-driven interfaces

Avoid:
- Promotional headings and subtitles inside operational screens.
- Long explanatory paragraphs where a short label or clear control is enough.
- Repeated descriptions of what obvious features do.
- Unnecessary introductions that push the actual task below the fold.
- Tutorial-style copy on routine screens.
- Feature cards that merely describe functionality instead of enabling it.
- Demo-style layouts that prioritize explaining the product over using it.
- Repeating the same information in headings, descriptions, labels and helper text.

## Product copy

- Use concise, natural, task-oriented language.
- Name actions clearly using familiar verbs.
- Show guidance only when it resolves a genuine ambiguity or prevents an error.
- Put detailed explanations in contextual help, documentation or progressive disclosure when appropriate.
- Do not remove necessary instructions, accessibility labels, legal notices, safety warnings or confirmation details merely to make a screen shorter.
- Avoid vague marketing language, filler and self-congratulatory copy.

## Functional priority

Prioritize:
1. The user's immediate task.
2. The content and controls needed to complete it.
3. Clear status and feedback.
4. Secondary actions and contextual help.

Do not make every screen look like a landing page or dashboard. Choose a layout that fits the actual workflow.

## Review questions

- Can the user understand what to do without reading an essay?
- Is the primary task immediately accessible?
- Is any copy repeating information already obvious from the control or context?
- Does the screen feel like working software rather than a prototype presentation?
- Have necessary guidance and accessibility information been retained?

## Principle

Design the product, not a presentation about the product.
